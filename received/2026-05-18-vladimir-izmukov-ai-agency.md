# Архитектурная стратегия AI-продюсерского агентства для мультиклиентского масштабирования

## Резюме задачи

Владимир строит агентство, которое будет вести 10–20 экспертов параллельно (контент, воронки, продажи). Сейчас соло-модель на себе работает идеально через Director-агента + gbrain-memory. Нужна архитектура, которая это клонирует без потери приватности, quality и с положительной экономикой.

---

## Рекомендуемая архитектура

### 1. **Память клиента: намеспейсированный gbrain + изолированный Postgres per-client**

**Решение:**
- **Основной слой:** gbrain-memory остаётся как быстрый semantic cache (tone, кампании, рабочие промпты). Каждому клиенту — отдельный namespace в единой gbrain-инфраструктуре.
- **Изолированный слой:** **отдельный Postgres-инстанс per-client** (или отдельная схема в одном Postgres, но с SQL-уровневым access control). Туда живёт: IG-логины (зашифрованы), токены Prodamus, истории контента, сырые метрики, лог-файлы ошибок.
- **Разделение:**
  - gbrain (Markdown) → быстрые контекстные запросы агентов
  - Postgres → долгосрочные данные, audit-trail, compliance-логирование

**Трейд-офф:**
✓ Полная изоляция + быстрый поиск
✗ Небольшой оверхед на управление N схем; нужен миграционный слой

---

### 2. **Штат агентов: гибридный подход (7–9 ролей + динамический пулинг)**

**Архитектура не «один на всех» и не «клон на каждого», а среднее:**

```
┌─────────────────────────────────────────┐
│  Load Balancer / Task Router            │
│  (Claude Code + custom orchestrator)    │
└────────────┬────────────────────────────┘
             │
    ┌────────┼────────┐
    │        │        │
[Сценарист] [Режиссёр] [Маркетолог]
  (1x)      (1x)      (1x)
    │        │        │
    └────────┼────────┘
             │
      [Shared Skills Pool]
    ├─ reels-analyzer
    ├─ carousel-reskinner
    ├─ reel-reskinner
    ├─ copyrighter
    ├─ designer-carousel
    └─ smm-planner
```

**Почему гибридный:**
- **Глобальные агенты** (Сценарист, Режиссёр, Маркетолог) — **1 на всех клиентов**. Они work-agnostic, просто берут `client_id` как параметр и переключают контекст через gbrain-namespace. Это экономит на compute.
- **Параллелизм на уровне tasks:** не один агент делает все для всех клиентов, а очередь задач (в памяти на Python asyncio или Redis queue). Задача = (client_id, task_type, payload).
- **Масштабирование:** если один Режиссёр начинает bottleneck (ждёт FAL-ответов), запускаешь второго на другом сервере (можно через контейнеризацию или функции).

**Кто владеет:** Сценарист пишет идею → Режиссёр получает её, набирает сценарий, делает timeline → Маркетолог смотрит, может ли это work вирально; параллельно запускаются render-скиллы.

### 3. **Onboarding клиента: 1–2 часа автоматизированно**

**Сценарий:**

1. **Интеррогация** (~30 мин):
   - Клиент заполняет структурированную форму (Telegram бот или web-форма): ФИО, что продаёт, целевая аудитория, ссылки на IG/TG/Notion.
   - Агент Маркетолог-Интервьюер (отдельный short-lived agent) пишет его в gbrain-namespace как **User Profile**.

2. **Фото-референсы и Soul Character** (~30 мин):
   - Клиент загружает 3–5 фото себя в разных сценариях (студия, на улице, с продуктом).
   - FAL Nano Banana 2 или Higgsfield генерирует на основе этого его **Soul Character ID** (константа для дальнейших нейро-видео).
   - ID сохраняется в Postgres.

3. **Tone & Style Guide** (~30 мин):
   - Маркетолог анализирует его существующие посты (если есть), берёт его tone-примеры, пишет в gbrain.
   - Дизайнер генерирует 3 вариантов palette-шаблонов (на основе брендовых цветов), клиент выбирает.

4. **Воронка-skeleton** (~1 час, параллельно):
   - Копирайтер пишет шаблоны прогревов (отправляются как examples, клиент утверждает).
   - СММ-плейнер рисует условную сетку (10 постов на две недели, типовые темы).
   - Админ-скрипт создаёт ему отдельный TG-бот (кода 50 строк, через aiogram + Prodamus-интеграция).

**После этого:** агенты готовы работать. Первый контент может быть сгенерирован в день 2.

---

### 4. **Изоляция данных и пропускание контекста**

**Уровни защиты:**

| Уровень | Механизм | Как это работает |
|---------|----------|-----------------|
| **Memory** | namespace isolation в gbrain | Агент делает recall только в `namespace: {client_id}` |
| **Database** | Postgres schemas / SQL ACL | Отдельная схема per-client; queries с `WHERE client_id = ?` |
| **Secrets** | Vault / .env per-client | API-ключи, пароли IG хранятся зашифрованы; агент запрашивает через secure endpoint |
| **LLM context** | System prompt с `client_id` | В каждом запросе Claude: `Ты работаешь для клиента {client_id}. Не смешивай контексты других клиентов.` |
| **Output filtering** | Post-processing агента | Перед возвратом результата агент чекит: `Это для {client_id}? Нет ли чужих данных в ответе?` |

**Как НЕ смешать данные:**
- Не использовать единый контекст на всех (это гарантирует утечку).
- Использовать явный параметр `client_id` в каждом запросе, памяти, функции.

### 5. **Оркестрация параллельных pipelines: Celery + Redis queue**

**Архитектура:**

```
TG-бот / Web → Task Creator → Redis Queue
                                 │
              ┌──────────────────┼──────────────────┐
              │                  │                  │
          [Worker 1]         [Worker 2]         [Worker 3]
          (рендер video)     (write caption)    (analyze competitor)
              │                  │                  │
              └──────────────────┼──────────────────┘
                                 │
                          Result Store (Postgres)
                                 │
                          Notification → Client
```

**Почему Celery:**
- Redis держит очередь, workers берут задачи асинхронно.
- Один долгий `FAL.image_to_video()` не блокирует другие задачи.
- Легко масштабировать: добавляешь worker, и автоматически распределяется.

**Пример задачи:**
```python
@celery.task(name="render_reel")
def render_reel(client_id: str, scenario: dict):
    agent = ReelsAgentFactory.get(client_id)
    result = agent.render(scenario)
    save_to_db(client_id, result)
    notify_client(client_id, result)
```

**На малых объёмах (10 клиентов, 200 рендеров/неделю):** одного Redis-экземпляра + 2–3 Python воркеров достаточно. Может жить на том же VPS, что сейчас.

### 6. **Human-in-the-loop: утверждение только финала**

**Модель:** **Auto-publish + Manual Review**

1. **Автоматическое генерирование:** Сценарист → Режиссёр → дизайнер → копирайтер → финальный рендер. Это 2–4 часа.
2. **Уведомление мне:** через Telegram приходит сводка (thumbnail + caption + metadata), я смотрю 30–60 сек.
3. **Действия:**
   - Approved → публикуется в соцсетях.
   - Rejected → агент получает feedback, переделывает (обычно 1–2 итерации).
   - Edit → я пишу конкретно что менять, агент исправляет.

**Критические моменты (требуют мануального review):**
- Первый пост клиента (задаёт tone).
- Контент с потенциально спорным мнением.
- Высокобюджетные кампании (500k+ ₽ за месяц).

**Остальное:** автопублиш после генерирования.

### 7. **Безопасная аутентификация клиента: OAuth 2.0 + Delegation**

**Проблема:** клиент не должен давать мне пароль от IG.

**Решение:**

- **IG/Meta:** Использовать Instagram Graph API с OAuth 2.0. Клиент кликает «Разрешить доступ моему аккаунту» → мы получаем refresh token на 60 дней → сохраняем зашифрованным в vault.

- **Telegram:** `BotFather` даёт бота клиенту, он даёт нам token боту (это уже делегирование, token можно менять).

- **Notion / Google Docs:** OAuth 2.0 (Google, Notion API поддерживают).

- **Prodamus / платежи:** API-ключ клиента (или делегированный ключ через специальный endpoint).

**Хранение secrets:**
```python
# Вместо .env в открытом виде:
from cryptography.fernet import Fernet

vault = {
    f"client_{client_id}_ig_token": encrypt(token, master_key)
}

# При использовании:
token = decrypt(vault[f"client_{client_id}_ig_token"], master_key)
```

## Unit-Economics & Cost Structure

### Текущие Costs (соло):
- **API:** $300/мес (Anthropic, FAL, HikerAPI, Groq, etc.)
- **Инфра:** ~$50/мес (VPS, Redis, Postgres)
- **Итого:** ~$350/мес ($4 200/год)

### Per-Client Costs (гибридная архитектура):
| Item | Cost | Notes |
|------|------|-------|
| Anthropic API calls | $30–50/мес | ~5–10k tokens/день per client |
| FAL/Higgsfield renders | $20–40/мес | ~40–80 видео/мес per client |
| Storage (video clips) | $5–10/мес | ~100–200 GB/год per client |
| Postgres schema | ~$2/мес | Fractional allocation |
| Redis queue | ~$1/мес | Fractional allocation |
| **Subtotal per-client** | **$58–103/мес** | — |

### Fixed Costs (на всех):
- VPS (улучшенный) для Celery/Redis: **$100/мес**
- Backup & monitoring: **$50/мес**
- **Total fixed:** **$150/мес**

### Модель выручки (примерные тарифы):
- **Tier 1:** 150 000 ₽/мес (~$1 850)
- **Tier 2:** 250 000 ₽/мес (~$3 100)
- **Tier 3:** 500 000 ₽/мес (~$6 200)

### Пример калькуляции (10 клиентов, средний mix):
```
Revenue:        10 клиентов × 250 000 ₽ = 2 500 000 ₽/мес
Costs:
  - API/Infra:  (10 × $80) + $150 = $950 (~76 000 ₽)
  - My time:    ~10 часов/неделю × 5000 ₽/час = 200 000 ₽
  - Misc:       50 000 ₽

Gross Profit:   2 500 000 - 76 000 - 200 000 - 50 000 = 2 174 000 ₽
Margin:         ~87%
```

**Вывод:** модель положительна даже на 5 клиентах. Масштабируется линейно до 20–30 клиентов (потом нужно будет нанять 1–2 человека на утверждение контента).

## Альтернативные подходы (почему не их)

| Подход | Почему нет |
|--------|-----------|
| **Один агент на каждого клиента (× 10 серверов)** | Overkill на compute; $150/мес × 10 = $1500/мес, не окупается при Tier 1 тарифе. |
| **Multi-tenant LLM context** | Риск cross-contamination; нарушение privacy. |
| **CrewAI без оркестрации** | CrewAI хорош для одной задачи, не для 200 параллельных. |
| **Полная автоматизация без human-in-loop** | Компромисс с качеством; контент нужно утверждать. |
| **Найм SMM-мэна вместо агента** | Люди дороже ($1500–3000/мес), медленнее, масштабируются хуже. |

### Подвопрос 1: Архитектура команды агентов для *себя самого*

Для своего @reelsmentor_ai нужны:
1. **Сценарист** → идеи хуков, структура Reels
2. **Режиссёр-планировщик** → съёмки/нейрогенерации, timeline
3. **Маркетолог-конкурент** → анализ чужих Reels (ChatPlace + reels-analyzer)
4. **Копирайтер** → captions + прогревы в TG
5. **Дизайнер** → карусели (PIL + шаблоны)
6. **СММ-плейнер** → сетка 20–40 постов в месяц
7. **Публикатор** → автопост в IG/TG (ChatPlace + Telegram Bot API)

Они передают артефакты через **gbrain-swarm** (отправляют друг другу промежуточные результаты) и **unified artifact store** (Postgres BLOB или S3 для видео/картинок).

Финальная публикация владеет **Публикатор**, я только даю сигнал ✅.

### Подвопрос 2: Контент-фабрика 10–20 постов в день

**Масштабирование на N постов:**

- **Ideation** (Сценарист): за 2–3 часа генерирует 20–30 идей (бранчей) для трендов дня.
- **Параллельный рендер**: каждую идею берут 2–3 воркера, могут делать одновременно (если есть Celery с 5+ воркерами).
- **Auto-approval для типичных**: если контент попадает в "approved template" (например, стандартный carousel с шаблоном), публикуется без мануального review.
- **Feedback loop**: неудачные контенты анализируются, их паттерны запоминаются и вычитаются из следующего батча.

**Механика без моих ручных корректировок:**
- Дизайнер использует **фиксированные шаблоны** (3–5 palette variants), не произвольные макеты.
- Копирайтер пишет captions по **структурному шаблону** (hook + body + CTA).
- Если нужна правка, она идёт в агента, а не мне (я только approve/reject на уровне идеи).

### Подвопрос 3: Сетка 10–20 аккаунтов (farming без банов)

**Техническое решение isolation:**

```
Device Fingerprint:
├─ iPhone 11 (SIM A) → Account 1-3
├─ iPhone 12 (SIM B) → Account 4-6
├─ Mac Mini (VPN A) → Account 7-9
└─ Android (VPN B) → Account 10-12

IP Rotation:
├─ Proxy 1 (geo A) → devices 1-4
├─ Proxy 2 (geo B) → devices 5-8
└─ Residential proxy → devices 9-12
```

**Правила:**
- Один аккаунт = одно устройство (физически или виртуально).
- Разные SIM-карты или мобильные провайдеры.
- Разные IP (резидентские прокси, не дата-центры).
- Content variation: один и тот же Reel публикуется в 3–5 вариантах (разные captions, разные thumbnails), не copy-paste.
- Эпизодичность: не 24/7 постинг, а 2–4 раза в день, с естественными перерывами.

**Через API или через приложение:**
- Лучше через **Instagram Graph API** + **Telegram Bot API** (не через скрапинг).
- Если нужен скрапинг (анализ конкурентов), то read-only режим, через HikerAPI / instagrapi.

## Заключение

**Критерий успеха:** спроектированная архитектура позволяет взять **1 тестового клиента** через неделю, а **5 платящих** через месяц после MVP, при положительной unit-economics и полной изоляции данных.

Гибридный подход (общие агенты + клиентские namespaces + Celery) лучше всего балансирует масштабируемость, стоимость и приватность.

## Ответ принца

_Дата ответа: 2026-05-29_

Владимир, ты прислал не вопрос, а готовую архитектуру под 20 клиентов — разбираю её критически, потому что именно это тебе сейчас полезнее всего.

### Диагноз

Архитектура спроектирована под 20 клиентов, а у тебя **ноль платящих**. Ты строишь масштаб до того, как доказал unit-экономику. Celery, отдельный Postgres per-client, output-filtering-агент — это решения для боли, которой у тебя ещё нет. Изоляция на старте стоит **одной колонки `client_id` и одного namespace**, а не отдельной инфраструктуры. Сократи MVP до «один платящий клиент за 30 дней».

Ты уже построил то, что у большинства только в голове — рабочего агента. Не строй вторую систему «на вырост». Проведи одного платящего эксперта руками через свою модель с одним `client_id` — пусть он, а не диаграмма, скажет, что усложнять.

### Изоляция ≠ отдельная инфраструктура

- **Один Postgres, колонка `client_id` везде** — row-isolation через один data-access слой. 95% изоляции за 5% усилий. БД — self-hosted Supabase на РФ-серваке (Timeweb/AdminVPS): один сервак закрывает Postgres + API + Auth + Storage под клиентские артефакты.
- **Один gbrain, namespace = `client_id`** — ты это уже умеешь, не трогай.
- **Агенты work-agnostic, `client_id` — обязательный параметр** в каждом запросе, памяти и функции.
- **Output-filtering-агент — выкинуть.** Это костыль поверх дырявой изоляции. Чини причину (забыть `client_id` должно быть ошибкой контракта), а не симптом.
- **Секреты — Fernet/pgcrypto в Postgres.** Vault — оверкилл на 10 клиентов.

### Когда добавлять усложнения (триггер-метрики, не «заранее»)

| Усложнение | Триггер |
|---|---|
| Celery/Redis | когда синхронный рендер реально блокирует другого клиента (p95 в очереди > SLA) |
| Postgres per-client | когда клиент по договору требует физической изоляции, либо таблица перевалила за десятки млн строк |
| RLS-политики | когда к БД получает доступ второй человек |

До этих триггеров — один Postgres + `client_id`. Всё.

### 30-дневный MVP до первого платящего

- **Неделя 1 — параметризация.** Прогнать рабочую соло-модель через `client_id`: колонка в БД, namespace в gbrain, параметр в каждом агенте. Без новой инфраструктуры.
- **Неделя 2 — onboarding вручную + pipeline.** Скрипт-инициализатор клиента (твои 50 строк). Onboarding руками по чек-листу, не автоматизированно. Pipeline: идея -> сценарий -> рендер -> сводка в TG -> approve.
- **Неделя 3 — первый РЕАЛЬНЫЙ клиент.** Платящий, не друг. Замеряй: часы своего времени, $ токенов и рендеров, число итераций до approve.
- **Неделя 4 — замер и решение.** Реальная маржа на одном клиенте. Если сходятся и время, и деньги, и quality — тогда масштабируй на 5.

### Sanity-check экономики (твои 87% маржи)

87% — маркетинговая цифра, не операционная. Что её съедает:
- **Твоё время.** 1 час/нед на клиента нереально, когда «утверждаю» превращается в «переписываю за агентом».
- **Токены растут нелинейно.** Мультиагентный pipeline даёт x3–5 расхода, каждый reject = деньги дважды.
- **FAL/Higgsfield** — самый волатильный cost driver: 40–80 видео легко становятся 150+.

Реальная гипотеза до замера на первом клиенте — **50–60% маржи**, не 87%. Это всё равно отличный бизнес, но планируй от реальной цифры.

### На чём споткнёшься

- **Cross-contamination через gbrain** — `recall` без namespace = контент одного клиента всплывает у другого. Сделай так, чтобы забыть `client_id` было ошибкой контракта, а не рантайма.
- **Качество не масштабируется автопаблишем** — один плохой автопост на чужом аккаунте = потерянный клиент. Первые недели — review всего, авто-публиш только для проверенных шаблонов.
- **Фарм-сетка 10–20 аккаунтов** — бан + правовой риск, серая зона ToS Instagram. Это не часть agency-MVP, не вешай этот риск на платящих клиентов.

### Итог

Не строй вторую систему «на вырост». Проведи одного платящего эксперта руками через свою рабочую модель с одним `client_id`. Реальная маржа и реальное время на первом клиенте скажут тебе больше, чем любая диаграмма на 20 клиентов.
